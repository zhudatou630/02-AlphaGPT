# Stage D 新架构

**时间**：2026-07-14 07:37
**背景**：Stage D formal 原型在 batch 8192、800 万 attempts 规模下出现 GPU 长期等待单核 Python、候选状态和 checkpoint 持续膨胀的问题，需要先从第一性原理重做训练计算与状态架构，再开始正式实验。

**关键决策**：
- 最高约束 → 冻结研究内核，不冻结旧实现细节（备选：要求新旧 bit-identical）— 理由：尚无完整 formal run；必须保持训练数据、公式数学语义、reward、Transformer 与 matched-random 的公平预算和比较规则，但旧随机序列、文件格式和执行方式不是正确性标准。
- 旧 formal seed 101 → 仅保留为性能诊断材料，新架构建立新身份并从头跑六个 formal run（备选：续跑或混用旧结果）— 理由：旧代码是未完成原型。
- 总体计算流 → GPU 批量主流水线 + CPU 多核后台整理 + 单线程有序提交（备选：继续单循环串行）— 理由：独立重计算应并行，digest、去重、候选状态和 ledger 顺序必须集中提交。
- GPU 边界 → GPU 连续完成批量语法状态机、公式抽样、VM 指令生成、VM/scorer/backward；batch 结束后才批量交给 CPU（备选：每个 token 位置回 CPU 更新语法）— 理由：语法仅有 121 个可达状态，可用小型状态表消除逐公式 Python/GPU 往返。
- CPU 并行 → 多进程按块处理 AST、canonicalize、hash 和候选基础记录；单一提交器按 attempt 原始顺序更新全局状态并批量写 ledger（备选：线程或无序提交）— 理由：绕过 GIL，同时保持研究账本确定性。
- 流水线交接 → GPU 处理 batch N+1 时 CPU 整理 batch N；有界队列最多保留 1-2 批，checkpoint 前排空（备选：无限队列或完全串行）— 理由：重叠独立阶段，同时用背压控制内存和速度失配。
- 历史事实 → append-only ledger 是唯一事实来源，记录重建候选状态所需的完整最小字段（备选：在 checkpoint、多个 dict 和 ledger 中重复保存）— 理由：消除重复历史副本。
- 候选状态 → 内存紧凑索引 + 连续数组，只保存 hash、计数、首次/最佳位置、最佳 reward/token 和必要质量指标；完整表达式和全量 reward 不常驻内存（备选：嵌套 CandidateRecord 字典）— 理由：最终展示时可由 token 重建。
- 索引技术 → 先用内存紧凑索引和二进制快照，容量门禁不通过时才升级数据库（备选：一开始引入 SQLite/LMDB）— 理由：符合个人研究原型的简单性，110GiB 内存足以先验证。
- checkpoint → 小型训练 checkpoint 每 30 分钟；候选索引快照每 120 分钟；正常停止、收到停止信号和训练完成时额外保存（备选：每 10 batch 保存完整状态）— 理由：意外故障最多重跑 30 分钟，最坏重放不超过 120 分钟 ledger，不再高频复制巨大历史。
- 恢复一致性 → checkpoint 在 batch 提交边界建立屏障，先排空队列并落盘 ledger，再绑定模型/optimizer/RNG、ledger offset/hash 和候选快照位置（备选：异步保存互不绑定的状态）— 理由：模型、账本和索引必须指向同一 attempt 边界。
- 迁移方式 → 保留旧训练脚本作参考，另建新训练主线；验收后再替换旧主线（备选：在旧循环里持续打补丁）— 理由：本次改变的是整体调度和状态模型，不应长期混合新旧假设。
- 实施顺序 → 独立组件 → 串行新主线 → CPU 多进程 → GPU/CPU 双流水线 → 远端容量验收（备选：一次完成全部并发重写）— 理由：每一步只增加一种复杂度，便于定位错误。
- 正确性策略 → 开发期和正式训练前用少量关键验收证明正确；正式热路径只保留 loss/梯度有限、attempt 连续、队列边界、worker 异常和 checkpoint 提交位置等廉价检查（备选：逐公式重复深校验、影子执行和多层 fallback）— 理由：避免防御性编程重新成为瓶颈。
- 正式前门禁 → 898 机先跑 50 batch（409,600 attempts）；最低 1000 attempts/s、目标 2000+；CPU 内存外推小于 70GB、GPU 至少留约 5GB、单 run 小于 8GB、快 checkpoint 小于 5 秒、候选快照外推小于 60 秒、正常 resume 小于 10 分钟（备选：凭短 smoke 感觉直接放行）— 理由：800 万规模必须先做吞吐和容量规划。

**待定/未决**：新模块和文件边界、ledger 行的具体编码、紧凑数组格式、CPU worker 最优数量、GPU 缓冲区实现、容量外推后的数据库降级条件细节；这些属于实施设计，按阶段实测决定，不在架构共识中提前写死。

**事实依据**：
- `.pi/profile/2026-07-14——formal-s101性能体检结论.md`：正式副本 3 batch profiling 显示 GPU 利用率中位数 0%、均值 1.37%；GPU VM 累计约 1.24 秒、backward 约 0.36 秒；profile 绝对秒数受 cProfile 放大，只用于定位调用结构。
- `src/alpha_etf/research_v3a/sampling.py`：现实现每个 token 位置逐行处理 8192 个 GrammarState，并在 Python 循环中读写 GPU 标量。
- 本地穷举 `language.py` 冻结语法：词表 27 个 token，最长 15 token 时仅 121 个可达 GrammarState、759 个状态/长度组合、3343 条合法转移，适合表驱动批量实现。
- 898 实际 cgroup 配额为 22 vCPU、110GiB 内存；RTX PRO 6000 96GB。宿主机显示的 208 CPU/1TiB 不是可用配额。
- seed 101 在 737,280 attempts 时正式 run 约 1.03GB、checkpoint 约 556MB；完整 candidate_state pickle 和 resume 深校验会随历史增长。
- 正式 seed 101 checkpoint 与 ledger 在性能体检前后 SHA-256 完全一致，现有结果未被诊断修改。

**下一步**：基于本记录先设计新主线的最小模块边界和阶段 1 实施计划；经用户确认后再编码。任何 formal 训练必须等五阶段实现和 50-batch 远端门禁全部通过，并重新生成 research identity、train view binding 与 run 身份。
