# Stage D 性能体检

**时间**：2026-07-14 03:16
**背景**：确认 formal 训练单步约 24 秒的真实耗时构成，再决定是否以及如何优化。

**关键决策**：
- 优化前先做性能体检 → 同意（备选：直接去重或上多进程）— 理由：本机微基准不支持 canonicalize 占主要瓶颈的原判断，直接并行可能优化错对象。
- 体检对象 → 898 机上 seed 101 正式 run 的临时副本（备选：直接续跑正式目录）— 理由：不改变正式 checkpoint 和 attempts ledger。
- 体检长度 → 从副本 checkpoint 续跑 3 个 batch，共 24,576 attempts（备选：1 或 10 个 batch）— 理由：兼顾 CUDA 预热、正常训练和结束 checkpoint，成本可控。
- 执行边界 → 第一轮只做无侵入体检（备选：同时修改训练代码做精确打点）— 理由：保持旧 code fingerprint 和身份链，不让体检演变成优化实施。
- 关机策略 → 诊断文件确认落盘后自动关闭 898 机（备选：保持开机等待确认）— 理由：避免分析期间继续产生 GPU 租金。

**待定/未决**：真正瓶颈、是否需要多进程、candidate ledger 是否要紧凑化、优化后六个 run 是否全部重跑；均待第一轮体检数据后决定。

**事实依据**：
- 898 配置由用户截图确认：RTX PRO 6000 96GB、22 vCPU、110GB 内存、500GB 免费数据盘。
- `scripts/v3a/train_gpu.py:562-705` 存在 compile/canonicalize/hash 的条件性重复计算，同时逐公式读取 GPU scalar。
- `src/alpha_etf/research_v3a/stage_d.py:677` 的 `retain_candidate` 会重建、校验和排序候选记录。
- 本机 8192 条、平均约 14 token 的微基准：compile 约 0.51 秒、canonicalize 约 0.32 秒、hash 约 0.12 秒、全部 build record 约 1.36 秒、全部 retain 约 3.23 秒；不足以单独解释 24 秒。
- `scripts/v3a/runtime.py:46` 表明 `src/alpha_etf/research_v3a/*.py` 和 `scripts/v3a/*.{py,sh}` 会进入 code fingerprint；诊断脚本因此放在 `.pi/profile/`。
