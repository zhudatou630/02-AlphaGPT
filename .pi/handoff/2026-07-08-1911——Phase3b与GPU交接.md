## 关键发现与风险

### 1. 工程闭环通过，但训练质量未证明

模型学会了少写坏公式：

```text
step 1 valid_rate = 71.9%
step 500 valid_rate = 100%
```

但 best formula 出现在第一批：

```text
train_000001_021
```

后续没有刷新最高 reward。当前不能证明模型已经超过随机搜索。

### 2. 小 batch 和探索收缩可能是主因

当前 `batch_size=64`，而原作者主线是 `8192`。小 batch 下 REINFORCE 梯度估计很吵。

训练 entropy 下降明显：

```text
step 1 entropy ~= 41.64
step 500 entropy ~= 1.96
```

说明后期探索明显收缩。

### 3. EOS 没有自动让公式变短

最终：

```text
avg_formula_len = 16.0
```

EOS 只是允许提前结束，不会自动鼓励提前结束。当前 reward 没有惩罚长公式或冗余 token，因此模型倾向写满 `max_len`。

### 4. 最优公式有冗余和极端值问题

最优公式 token：

```text
low ABS DECAY MA10 MA5 RET10 RET10 ABS CONST_1 DELAY1 SIGN RET5 DELAY10 ADD DELAY1 MA10
```

其中：

```text
CONST_1 -> DELAY1 -> SIGN -> RET5 -> DELAY10
```

基本是零项，删掉 reward 不变。`RET10(RET10(...))` 可能制造极端信号，最大信号值约 `1.56e13`。

后续需要考虑：

```text
signal normalization
clip / winsorize
长度惩罚
公式简化/去冗余
```

### 5. rank_only validator 是必要的

Phase3a 暴露 raw signal 零轴问题。Phase3b 已新增 `rank_only` 审计，不改 Phase2B 原始 validator。

### GPU 性能适配思路

先不要上更贵 GPU。当前 4090D 足够，重点是判断瓶颈：

```text
如果 GPU 利用率高，batch 放大能明显提速：继续扩大 batch 和 steps。
如果 GPU 利用率低，CPU 满载：优先优化 VM/scorer。
```

潜在优化方向：

```text
1. 把公式评估批量化，减少 Python for-loop。
2. 用 numpy 向量化/预缓存 open_prices/mask/dates。
3. 减少 pandas 在训练内循环中的使用。
4. 训练时只记录必要字段，完整 sampled_formulas 可按间隔写。
5. 考虑对 scorer 做 numba/torch 化，但先测瓶颈再改。
```

不建议现在直接接入 LoRD/MTP/LoopedTransformer。增强组件未来有价值，但应等 GPU 性能和 reward/探索问题摸清后再加。
