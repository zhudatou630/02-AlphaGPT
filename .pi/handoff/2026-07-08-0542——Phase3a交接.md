## 关键决策及理由

| 决策 | 选定项 | 理由 |
|---|---|---|
| Phase3 拆分 | Phase3-0 → Phase3a → Phase3b | 先暴露环境风险，再验证公式管线，最后接模型训练，降低排错维度 |
| PyTorch 环境 | 项目内 `.venv`，CPU 版 PyTorch | 本机无 NVIDIA GPU；当前数据规模小，CPU 足够跑最小闭环；隔离环境避免污染全局 Python |
| Phase3a 定位 | 不训练模型的公式测试台 | 先证明 token 公式、VM、scorer、artifact、validator 审计链路可靠 |
| VM | StackVM | 继承 AlphaGPT 的公式 token 执行思想；使公式从 Python 函数变成可生成、可保存、可复现的 token artifact |
| 词表 | 时序 token 起步，不上横截面 token | 当前 ETF 池小，scorer/validator 已做 top-K 横截面选择；横截面 token 会提前引入 mask、动态 universe、前视和排序语义复杂度 |
| 常数 token | 加 `CONST_0`、`CONST_1` | `mom_10`、`ma_gap` 需要 `-1` 保留零轴语义；更多常数会扩大搜索空间 |
| 条件/门控 token | 第一版不加 | `GATE/IF/MAX/MIN/CLIP` 会增加非法率、稀疏信号和排错难度，留到第二波表达力升级 |
| 随机生成器 | 栈深度约束的半受控随机 | 比完全随机更少无效公式，比严格语法树简单，且与 StackVM 语义一致 |
| 非法公式 | 不丢弃，记录 `invalid_reason` 并给低 reward | 后续 REINFORCE 需要知道坏公式长什么样；invalid 分布能诊断词表和生成器问题 |
| reward | 合法公式用 `scorer_mean_return`，`horizon=10` | 直接沿用 Phase2 scorer 主口径；其它 scorer 指标只记录不混入 reward |
| validator | 只审计 best formulas，不进入 reward | 保持 scorer/validator 分层；审计用于发现交易层不一致，而不是训练目标 |
| 产物目录 | `data/processed/phase3a/` | 与未来 Phase3b 训练产物分开 |
