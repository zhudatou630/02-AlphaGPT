# Formal seed 101 性能体检结论

**时间**：2026-07-14
**范围**：正式 run 的临时副本从 737,280 续跑至 761,856 attempts（3 batch）；正式 checkpoint 与 ledger 未修改。

## 结论

原先“canonicalize 占正常单步约 70%，应优先用多进程并行”的判断不成立。正常训练中更重要的 CPU 工作是：

1. `sample_formulas` 每个 token 位置都用 Python 逐条处理 8,192 个语法状态，16 轮共约 39 万次逐行决策；GPU 在大量时间内等待 CPU。
2. 每个语义有效公式重复 `compile + canonicalize + hash`，随后 `retain_candidate` 又重建和校验候选记录。
3. checkpoint 随完整 canonical ledger 增长；当前正式 run 目录约 1.03GB，checkpoint 约 556MB，后续保存成本会继续增加。

不应把本次 375 秒总耗时直接除以 3：其中包含恢复时对 737,280 条历史状态的深度校验，以及结束时保存大型 checkpoint；`cProfile` 对数亿次 Python 调用也有明显放大效应。

## 证据

- cgroup 配额：22 CPU、110GiB 内存；`lscpu` 显示的 208 CPU 和 `free` 显示的 1TiB 是宿主机视图，不是可用配额。
- 3 batch 共 24,576 attempts，GPU VM 累计约 1.24 秒，backward 累计约 0.36 秒（profiler 归因值）。
- `sample_formulas`：3 次累计 90.58 秒，其中 `build_action_mask` 48 次累计 82.05 秒；受 cProfile 放大，但调用结构确认是串行热点。
- 正常后处理：`retain_candidate` 24,575 次累计 25.11 秒；重复 `build_candidate_record` 累计 8.51 秒；selection hash 累计 2.92 秒；ledger JSON 累计 0.41 秒；sequence digest 累计 0.27 秒。
- 恢复专属开销：`validate_training_candidate_state` 2 次累计 111.93 秒，`candidate_record_from_dict` 共 374,324 次累计 146.81 秒；主要来自扫描历史 canonical ledger，不代表每个正常 batch。
- 保存专属开销：一次 pickle dump 累计 77.54 秒；同样受 cProfile 放大，但确认 checkpoint 已是不可忽略的大对象。
- 352 个 GPU 采样点：利用率中位数 0%，均值 1.37%；显存峰值 92,809MiB。
- 进程 RSS 峰值约 7.3GiB；正式 run 原目录约 1.03GB。

## 推荐优化顺序

1. 先做低风险去重：复用已经得到的 compiled、canonical 和 hash；一次性把 `training_rewards` 搬到 CPU。
2. 简化正常候选入库：避免 `retain_candidate` 对刚构造且可信的记录再次 compile/canonicalize/hash。
3. 再优化采样器：把逐条 Python 语法状态和 action mask 改成批量表示；这是比 canonicalize 多进程更有潜力、但验证要求更高的改动。
4. 单独评估 checkpoint/canonical ledger 的增长；决定是否需要紧凑存储。它影响长 run 后半程和恢复时间，不应与正常单步混为一谈。
5. 暂不实施 ProcessPool canonicalize。只有完成前三步后，剩余计时仍证明它足够重，才值得引入多进程。
